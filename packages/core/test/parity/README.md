## What this directory is for

`physics.ts` is a hand-port of `reference/godot/scripts/PhysicsEngine.gd`. The only way
to know a port is *actually* right — not just "looks right" — is to replay the same
input against both engines and diff the trajectories in float64. That is what
`parity.test.ts` does, against trace files generated by `tools/godot-trace/trace.gd`
running inside the real Godot 4.6 engine, against the real `SwingBy2026` checkout.

## How to generate the traces (run this on the host, not in this container)

```bash
cd /path/to/SwingBy_web
/Applications/Godot.app/Contents/MacOS/Godot --headless \
  --path /path/to/SwingBy2026 \
  --script tools/godot-trace/trace.gd
```

Run this from the `SwingBy_web` repo root (`trace.gd` writes its output using paths
relative to the process's working directory, not `res://` — the output lives outside
the Godot project). `--path` must point at a checkout of `MagnusSaurbier/SwingBy2026`
(the project `reference/godot/` was snapshotted from) so that the real `PhysicsEngine`
and `GameConstants` classes are loaded — this script calls them directly, it does not
reimplement them. Requires Godot **4.3 or later** (uses `JSON.stringify`'s
`full_precision` parameter, added in 4.3, without which floats get truncated to a
handful of significant digits and every tolerance in this suite becomes meaningless).

This writes 33 files: `traces/level-00.json` through `traces/level-32.json`, one per
entry in `reference/godot/data/levels_builtin.json`, in array order (`level-00.json` is
`levels_builtin.json[0]`, etc). Commit them — they are the ground truth and must survive
without Godot installed, per the project's own rule that invented traces are worse than
missing ones.

**Determinism check (do this once, by hand):** run the exporter twice in a row and
`diff` the two output directories. They must be byte-identical. If they are not, one of
two things is non-deterministic and must be found before the traces mean anything: (a)
`turn_speed`'s `randf_range` leaking into a field this script exports (it should not —
`trace.gd` seeds it to a fixed constant and the exported schema omits `angle` and
`turnSpeed` entirely, see "Why `angle`/`turnSpeed` are excluded" below), or (b) something
else in the engine path. `trace.gd`'s own inline comments point at the seeding call.

## File format

One file per level, `level-NN.json` (`NN` = zero-padded level index, matching
`reference/godot/data/levels_builtin.json` array order — the same order T-03 ATLAS's
`BUILTIN_LEVELS` is expected to preserve). Schema:

```jsonc
{
  "schemaVersion": 1,
  "levelIndex": 0,
  "levelName": "Orbital Primer",       // levels_builtin.json[i].name, for cross-checking
  "goalIndex": 2,
  "goalRange": 64.0,
  "playerIndex": 0,

  // Fully-hydrated runtime bodies, in `objects` array order, at tick 0 — i.e. the
  // state PhysicsEngine ever sees, with every optional field defaulted exactly as
  // GameWorld._create_runtime_object defaults it. Field names are camelCase, matching
  // packages/core/src/types.ts's `Body` MINUS `angle` and `turnSpeed` (see below).
  "initialBodies": [
    { "type": "player", "x": 720, "y": 300, "xVel": 1.22, "yVel": -0.44,
      "xAcc": 0, "yAcc": 0, "gravity": 0, "size": 12, "visible": true,
      "anchored": false, "isBoosting": false, "isBraking": false, "boostType": 1 },
    ...
  ],

  // 2000 ticks, zero input throughout, sampled every 10 ticks INCLUDING tick 0
  // (201 samples: 0, 10, 20, ..., 2000). Definition-of-done bound: max abs position
  // divergence < 1e-6 world units against physics.ts replaying the same tape.
  "zeroInput": {
    "totalTicks": 2000,
    "sampleEveryTicks": 10,
    "samples": [
      { "tick": 0, "bodies": [ /* same per-body shape as initialBodies */ ] },
      { "tick": 10, "bodies": [ ... ] },
      ...
    ]
  },

  // Same 2000 ticks, same sampling, but driven by the canonical scripted boost/brake
  // tape defined below instead of zero input. Same < 1e-6 bound.
  "scriptedInput": {
    "totalTicks": 2000,
    "sampleEveryTicks": 10,
    "boostTransitions": [50, 150, 500, 650, 1200, 1350],
    "brakeTransitions": [700, 760, 1500, 1650],
    "samples": [ /* same shape as zeroInput.samples */ ]
  },

  // recalculate_predictions(objects) called ONCE on the pristine initial state
  // (tick 0, before any simulation). Compared sample-for-sample against predict()
  // called on the same reconstructed World.
  "prediction": {
    "player": [ { "x": ..., "y": ... }, ... ],
    "planets": [ [ { "x": ..., "y": ... }, ... ], ... ]   // one track per planet, body order
  },

  // ONLY present in level-00.json. 10,000 ticks, zero input, sampled every 100 ticks
  // (101 samples). Definition-of-done bound: < 1e-3 world units (drift accumulation
  // over a long run — a looser bound than the 2000-tick checks on purpose).
  "longRun": {
    "totalTicks": 10000,
    "sampleEveryTicks": 100,
    "samples": [ ... ]
  }
}
```

All floats are written with `JSON.stringify`'s `full_precision = true`, i.e. round-trip
losslessly through float64. `JSON.parse` in Node/the browser reconstructs them exactly.

### The canonical scripted input tape

`boostTransitions` / `brakeTransitions` use the same run-length convention as
`ReplayTape` in `types.ts`: the listed tick indices are where that control CHANGES
STATE, starting released. So `[50, 150]` means "pressed for ticks 50..149, released
otherwise." `parity.test.ts` and `trace.gd` each implement the same tiny
"is this control pressed at tick N" helper independently (T-01 does not import T-02's
`replay.ts` — see PROJECT.md's parallel-work rules) — if they ever disagree, that is a
harness bug to fix, not evidence about `physics.ts` itself. The transition lists above
are the literal values both implementations must use; they exercise boost, brake, a
release-then-repress, and — because `2000` ticks is well past `1650` — a long tail of
released input, all at fixed points so results are reproducible level to level.

Both boost and brake use whatever the level's `boost_type` renders as; type does not
affect physics.

### Why `angle`/`turnSpeed` are excluded

`GameWorld._create_runtime_object` seeds every body with
`"turn_speed": randf_range(-3.0, -2.0)` — a fresh random draw per load, so two Godot
runs of the same level produce different `angle` streams even though nothing about the
*trajectory* differs (no force calculation reads `turn_speed` or `angle` — see
`PhysicsEngine.gd`, `apply_gravity_acceleration` and `simulate_substep`/
`simulate_shadow_substep`: `angle` is written, never read back into `x_acc`/`y_acc`).
Asserting on it would make the suite flaky for a field with zero effect on solvability.
`trace.gd` seeds `turn_speed` to a fixed constant as defense in depth (so re-running the
exporter is itself deterministic), and additionally the exported schema simply never
includes `angle`/`turnSpeed`. Position and velocity are the ground truth.

## What the test suite does with this

- If `traces/` contains no `level-*.json` files, `parity.test.ts` **skips with a loud,
  explicit message** (via `describe.skip`/an explicit console warning plus a synthetic
  passing-but-labeled-skipped assertion) — it does not silently pass. See that file's
  top-of-suite check.
- Once traces exist, each level's `zeroInput`/`scriptedInput`/`longRun`/`prediction`
  sections are replayed through `physics.ts` starting from `initialBodies`
  (reconstructed directly as `Body` objects — `angle`/`turnSpeed` filled with `0`, which
  is safe precisely because of the independence argument above) and compared
  sample-for-sample. The suite prints the max absolute position divergence per level,
  per section — "a pass with no numbers reported is not a pass."
